# Working on paperpen

The manual, the demo film, and where the code comes from. Back to the [README](../README.md).

## The manual

`manual/` is a small site: what the thing is, reading a paper, writing it back,
putting it on the network, and every command in one page. It is committed as
finished HTML, so it can be read straight from the checkout, and any static
host publishes it by copying the directory: nothing is built, which is what
will still be true in a year. `.github/workflows/manual.yml` does exactly that
for https://acorbe.github.io/paperpen/ once Pages is on and the repository
variable `PAGES` is `on`, and `.github/workflows/tests.yml` runs
the tests on every push, TeX included.

```sh
scripts/manual.py                 # write manual/*.html from the text in that script
scripts/manual.py --check         # say whether what is committed is in step
scripts/manual-shots.py           # take the pictures again, out of the running app
python3 -m http.server -d manual  # read it here first
```

The workflow publishes `manual/` as it is; the address is the one GitHub Pages
gives the repository.

The pictures come from `demo/fixture.py` (invented papers, invented authors,
`example.org`) for the same reason the demo films do: nothing of anyone's
goes into a published picture, and a view that changes either still takes its
picture or fails loudly. `tests/test_manual.py` is the other half of that: no
home directory, no internal hostname, no private repository name and no address
outside the documentation ranges gets into a page.

## The demo

Three films, each generated by driving the program, never screen-grabbed.
`demo/fixture.py` invents four papers: four subjects and four relationships,
because those are what make the app behave differently, and one of them a real
LaTeX paper built here with SyncTeX, so the source lines in the films are the
ones the reader really worked out. A scenario per film drives the running app
in headless Chrome; `scripts/demo-gif.py` is the generic half and does not
know what it is filming. Nothing of this machine is in a frame: the fixture
lives under `/tmp/paperpen-demo`, and no page the films show prints it.

They move, because a film of a program being used should show the thing doing
the using. The pointer is real: the moves and the clicks are dispatched to the
page, so it hovers and opens what a hand would open it by, and each frame in
`frames.json` records where the pointer was for `scripts/demo-gif.py` to draw
it, a picture of a position and not an invention. Frames that share an image
share a file, so a pointer crossing a page that is not changing costs nothing.

**`demo/paperpen.gif`, the reading and the round** (`demo/scenario.py`). Eight
beats, 77 frames out of 29 images, 20.9 seconds: the shelf, the reader, a note
written by hand in the pad, the round sent, and the fixes coming back into the
notes. The note is written with a pen, a few strokes at a time with the
shutter open between them, so the handwriting appears the way handwriting
appears. `demo/handwriting.py` lays the words out as single-stroke letters and
`demo/chrome.py` walks them with `pointerType: "pen"`, which is what a stylus
sends and what the reader keys its whole pen behaviour on, so the ink in the
frame is ink the page worked out from a hand moving over the glass. The fixes
are proposed with the same code `paperpen propose` runs, against the fixture
paper's real LaTeX, and one tap on the first puts it into the source and opens
the second.

**`demo/review.gif`, Claude reading first** (`demo/scenario_review.py`). Seven
beats, 50 frames out of 16 images, 20.3 seconds: the reader on the fixture's
own paper; **Review** in the header and the focus typed, "clarity, notation";
the run started and the notes arriving in Claude's colour with their pins
ringed; one opened, its diff shown, approved, and the next one opening; that
one rejected with a reason; and the Fixes page, `/paper/<id>/feedback`, with
Claude's proposals picked out. No model is run. The notes are written with
`paperpen suggest` (`proposals.suggest`) from a scripted list against the
fixture paper's real LaTeX, so every diff on screen applies, and **Start the
review** is pressed for real with its one call to the server pointed at
nothing: the page then does what it does when a run reports back.

**`demo/editor.gif`, writing it back** (`demo/scenario_editor.py`). Seven
beats, 51 frames out of 19 images, 20.3 seconds: the editor with the file tree
and the build beside the source; a section opened from the tree; the line the
note was about edited, "roughly three times" to "about twice"; the build;
the build zoomed and the line double clicked, which draws the box SyncTeX
finds for it on the page; then the versions view, the last commit as old and
the working tree as new; and latexdiff between them, compiled and zoomed, with
the change marked up. The build and the diff are the real ones, latexmk and
latexdiff over the fixture paper.

```sh
uv run --with websocket-client python demo/scenario.py          # -> demo/frames/
uv run --with websocket-client python demo/scenario_review.py   # -> demo/frames-review/
uv run --with websocket-client python demo/scenario_editor.py   # -> demo/frames-editor/
uv run --with pillow python scripts/demo-gif.py demo/frames demo/paperpen.gif
uv run --with pillow python scripts/demo-gif.py demo/frames-review demo/review.gif
uv run --with pillow python scripts/demo-gif.py demo/frames-editor demo/editor.gif
python demo/handwriting.py "a phrase"    # -> /tmp/handwriting.svg, to look at
```

Each film is under a megabyte. The frames are kept as the browser hands them
over; the GIF is where the colours are cut, to one palette shared by every
frame so that a frame in which only the pointer moved is a few hundred bytes
rather than forty thousand. A scenario run builds the fixture afresh, so the
commit hashes in the headers change from run to run and nothing else does.

So a GIF cannot show something the program does not do, and when the
interface changes a scenario either still runs or fails loudly. Filming found
two. The pen: the pad took the `.empty` class meant for the page placeholder
and wore its 2rem padding until the first stroke landed, so the writing area
jumped the moment the pen touched it; that is
`upstream/patches/0002-the-empty-pad-is-not-the-empty-page.patch`. And the
editor: its highlighter read the `%` of `20\%` as the start of a comment and
greyed the rest of the line, so a per cent sign in the prose looked like a
comment; a backslash before anything that is not a letter is now taken as a
character.

## Where the code comes from

The reader grew inside a personal dashboard of the author's, a private
repository, and is exercised there daily, so `upstream/` holds that
repository's files verbatim and `scripts/sync.py` takes them again, from the
checkout named by `$PAPERPEN_BOARD`. Nothing here edits them by hand: what paperpen needs differently is
rebound at import (`paperpen/bind.py`), or is a patch in `upstream/patches/`
that the sync replays. `scripts/sync.py --check` says whether the two are still
in step and changes nothing. The dashboard's own checkout path, which its files
name, is taken out as they are copied (`scrub` in `scripts/sync.py`), with the
name worked out at sync time, since a patch would carry the old lines itself.

```sh
scripts/sync.py            # take upstream/ from the dashboard again
scripts/sync.py --check    # in step? exits non-zero when not
python -m pytest
```
